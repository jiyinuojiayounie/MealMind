# Public AI Planning · v0.2.1

The public portfolio site remains a Render Static Site. The optional public planner calls one dedicated HTTPS API origin. Saved plans use IndexedDB in the visitor's browser. Public food logging, nutrition and replanning use browser-local records and make no requests to the planning API.

## Server boundary

Run `app.public_planning:app` instead of the local development entry point. It registers only `POST /api/v1/meal-plans/generate` and handles CORS preflight only for that path. The only recognized query parameter is `infer_scope=true|false`. Frontend calls through the existing general API client remain prohibited in production. The public planner sends text to Gemini and avoids storing prompts, responses, user profiles and food logs. It logs a request ID, status, elapsed milliseconds, stage, attempt count, upstream HTTP status when available and numeric provider token metadata when present. Keep access logs disabled. Do not share keys with Vite.

The server records admitted request events for a rolling minute and UTC day per IP. IPs are pseudonymized with a dedicated server-side HMAC key. Rate counters expire after the applicable day/minute windows. The provider ledger reserves each attempt immediately before invoking Gemini. Daily and monthly attempt caps are evaluated in UTC. A failed attempt remains charged against the quota. The SQLite ledger uses atomic transactions and survives restarts. The database lives on the dedicated mount, contains quota counters only, and is initialized explicitly. A missing, locked or invalid database disables generation. The process limits generation concurrency to two. Use one instance and one worker with the persistent disk attached.

The request body is bounded at 16 KiB as it is streamed, with a five-second read deadline. The server also bounds serialized model input (request fields, system instructions and schema) to 16 KiB. This is a byte bound, not a claim about exact Gemini tokenization. The public entry point allows Gemini 3.1 Flash-Lite and Gemini 3.5 Flash-Lite, with minimal thinking, a configured 4,096 output-token limit, a 25-second upstream timeout, no automatic retry and no followed provider redirects. Use provider usage metadata for actual billing estimates.

## Render setup after activation approval

1. Create one paid Render Web Service using the reviewed revision of `jiyinuojiayounie/MealMind`, Python runtime, a blank Root Directory, and Auto-Deploy Off. Set `PYTHON_VERSION=3.14.8`. Set Build Command to `pip install -r backend/requirements.txt`.
2. Attach a separate 1 GB persistent disk at `/var/data`. With the generation switch off, initialize the ledger from the runtime shell using `cd backend && python -m app.storage.planning_quota /var/data/planning-quota.sqlite3`. Never reinitialize or replace the ledger to recover from a routine deploy. Keep the Web Service on one instance. Leave HTTP health-check path blank to use the platform port check.
3. Set Start Command to `uvicorn --app-dir backend app.public_planning:app --host 0.0.0.0 --port "$PORT" --workers 1 --no-proxy-headers --no-access-log`. Configure `GEMINI_API_KEY` as a server-only secret for a dedicated Gemini project, `GEMINI_MODEL=gemini-3.5-flash-lite` for the next controlled verification, `MEALMIND_PUBLIC_QUOTA_PATH=/var/data/planning-quota.sqlite3`, and `MEALMIND_PUBLIC_QUOTA_SECRET` as a stable random secret of at least 32 characters. Keep `MEALMIND_PUBLIC_PLANNING_ENABLED=false` until verification.
4. Confirm the Render ingress socket peer and forwarded-chain behavior for this workload before activation. Supply only the verified proxy networks in `MEALMIND_PUBLIC_TRUSTED_PROXIES` as comma-separated CIDRs. In proxy mode, the application rejects an untrusted socket peer and selects the first untrusted address looking from right to left. Use a controlled ingress test to verify that supplying fake left-hand addresses cannot change the visitor identity and that unrelated visitors do not share a proxy quota bucket. The empty setting is for direct connections such as local testing. Do not use a wildcard or assume private network ranges are trusted.
5. Verify the disabled and isolated service. After approval, set `MEALMIND_PUBLIC_PLANNING_ENABLED=true` and apply the updated runtime environment. Set `VITE_PUBLIC_PLANNING_ENABLED=true` and `VITE_PUBLIC_PLANNING_API_ORIGIN=https://<planner-service>.onrender.com` on the existing Static Site only, then manually rebuild it. The build command, publish directory and SPA rewrites stay as documented in [Portfolio Release](PORTFOLIO_RELEASE.md). The API's CORS allowlist is the exact current static-site origin.
6. Retest public planning and local save/replace, Blind Box, bilingual mobile layout and independent browser sessions. Probe the API origin directly for private routes and catalog/debug access. Recheck oversized streaming bodies, rate/quota admission, and the emergency switch. To turn generation off, set the server switch to false and apply the runtime environment. To restore the sample-only UI, disable the frontend flag and rebuild the static site.

## Cost and activation gates

The expected starting compute cost is about US$7/month plus US$0.25/month for a 1 GB disk, excluding taxes, bandwidth or workspace charges. Gemini 3.5 Flash-Lite Standard paid rates are US$0.30 per 1M input and US$2.50 per 1M output tokens including thinking. At the observed 594 input and 296 output tokens, the paid-rate equivalent is US$0.000918 per generation or US$0.46 per 500 comparable generations. The actual controlled generation used the free-tier project. This estimate excludes taxes, traffic and token variation. Review the provider project's data-use terms before sending public prompts. The free tier can use submitted content to improve Google products.

Activation requires verified ingress IP derivation, billed hosting and Gemini project approval, plus a hosted memory and latency check. A local test does not establish capacity on a 512 MB Render instance. Concurrency is capped at two, so test resource use with two parallel requests in a controlled environment before public activation.

References: [Render pricing](https://render.com/pricing), [Render persistent disks](https://render.com/docs/disks), [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing).

## Stage 2 browser-local food records

The production frontend uses a separate `food-logs` object store in the browser's meal database. The additive IndexedDB upgrade retains existing plans and plan history. Records preserve the local calendar date, offset, meal slot, original description, items and unknown quantities. Manual entries begin as drafts, with explicit confirmation, correction and deletion. Confirmed records appear separately from planned meals on Today. The development backend and its SQLite records are independent.

Plan acceptance checks confirmed local consumption and the current plan revision in one transaction. Confirmed breakfast, lunch, dinner or snack can lock only the corresponding local date and meal slot. Drafts, unspecified meal slots and Blind Box draws do not lock a plan slot. Browser storage belongs to one origin and browser profile, and clearing site data removes its local records.

Stage 3 may read these records by local date and status. Nutrition calculation and replanning remain previews. Manual free-text foods and household units still need verified matching and portion evidence before calculation.

## Stage 3 browser-local nutrition

The production Today nutrition panel reads only confirmed records for its selected local calendar date. It uses the existing 30-food USDA SR Legacy reference snapshot and the same reviewed matching vocabulary as Python. Exact bilingual reference names and approved food states can be calculated from edible mass or an existing food-specific portion conversion. Ambiguous names, conflicting preparation states, unsupported dishes, and missing amounts remain unresolved. A confirmed meal may produce a partial subtotal. Coverage describes recorded items only.

The nutrition module loads on demand and performs no network calculation. Browser floating point values are rounded only for display. The offline parity runner checks item decisions and source IDs exactly and compares numeric results with the Python Decimal fixtures within a relative tolerance of 1e-12. Run `node scripts/test_browser_nutrition_parity.mjs` at the repository root after installing frontend and backend dependencies. If the reviewed Python vocabulary changes, regenerate the browser snapshot with `(cd backend && .venv/bin/python -m scripts.export_browser_nutrition_rules) > data/nutrition/browser-rules-v1.json` and rerun parity.

Stage 4 can read confirmed food records for meal locks and use the nutrition coverage flags to distinguish unknowns. Any replan still needs explicit acceptance and date, revision and lock checks. Nutrition estimates do not establish a full day's intake or a calorie deficit.

## Stage 4 browser-local replanning

The public Today page replans one eligible slot on a selected local date using the nine content-reviewed Blind Box candidates. The form supports noodles, an estimated 20-minute maximum, and avoiding exact names from earlier confirmed foods and earlier planned dishes. It also preserves saved structured ingredient and time limits. The small pool can return no match. The user reviews dietary restrictions each time because prior free-text restrictions are not stored. A declared or uncertain restriction stops suggestions because the candidate pool lacks sufficient evidence.

Confirmed foods and explicit user locks protect matching slots. User locks live outside the immutable recipe snapshots and have their own revision. Preview and cancel do not write. Acceptance verifies the plan ID, revision, lock revision and confirmed-log IDs and revisions, and checks locks within the same IndexedDB transaction used to save a new plan revision. Only the chosen slot is merged. The public flow uses no AI or food-log API. It does not use nutrition estimates as targets. Private AI Replan remains available in its existing development environment.

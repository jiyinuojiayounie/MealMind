# MVP replanning design

Day 7 Replan design. Step 7.2A implements the shared browser-local plan repository. Step 7.2B implements the local backend context and preview. Step 7.3 implements the Today preview and browser acceptance. This design applies FR06 and the existing confirmation, privacy, and nutrition boundaries. [PRD](PRD.md) · [Decisions](DECISIONS.md) · [Product backlog](PRODUCT_BACKLOG.md)

## Verified baseline

- Before Step 7.2A, Planning held the generated `MealPlanResponse` and its language in PlanningPage component state. Navigating away or reloading lost the result. The generation API still returns a plan without a plan ID or date. Planning now saves only explicit acceptances through the shared browser repository. The Today meal overview is a placeholder; its nutrition card is wired to the daily analysis API. Previously generated suggestions were not migrated to the browser store.
- SQLite stores actual food logs and their revisions. Confirmed-only queries select by the local date in each recorded timestamp's offset. Drafts, deleted records, and planning responses are excluded. Only a confirmed log with an explicit meal type can lock that completed slot. A confirmed `unspecified` log is still actual consumption, and its timestamp alone cannot identify a slot.
- Daily nutrition estimates cover confirmed records, with per-nutrient coverage and `day_completeness: not_assessed`. Missing or partial analysis cannot establish a nutritional deficit. Food-log and nutrition routes are development-only with loopback checks.

## MVP user journey

1. On Today, select **Replan remaining meals**. Show today's date and which labeled meals have confirmed records. If a saved plan exists, display the current proposed meal beside the confirmed meal history as separate sections. When no plan exists, offer a suggestion for the next meal. Opening the panel or changing logs makes no model request.
2. Let the user select **one remaining meal** per request. After a confirmed lunch, dinner is the default suggestion. With no reliable ordering signal, require a choice. Show incomplete history explicitly. The user can mark a slot as already eaten for this preview, without creating a food log.
3. Present the applicable preferences and restrictions before generating. Carry forward selected planning mode, one-person preference, ingredient mode, current ingredient availability, and preparation effort/time constraints when supported. Ask the user to review inventory and requirements for the chosen meal. Missing logs and nutrient values are not blockers by themselves.
4. On explicit **Generate preview**, return a single proposed meal. Show the current meal and proposed change, what was actually confirmed, and which assumptions were used. Label proposals and nutritional data separately. Cancel keeps the current plan. **Apply to plan** replaces only the selected slot, or explicitly adds it if absent. With no plan, **Save as today's plan** creates a baseline only after acceptance. A suggestion that the user abandons requires no persistence.

### Remaining meals and edge cases

| Situation | Expected behavior |
| --- | --- |
| Confirmed lunch, breakfast unrecorded | Lock lunch, leave breakfast's status unknown, and suggest dinner. Do not replace the earlier breakfast slot. |
| Confirmed meal in a saved slot | Lock that meal type regardless of nutrient coverage or whether confirmed dishes differ from the plan. Keep its planned entry visible as planned and its food logs visible as actual. |
| No confirmed typed main meal or no previous plan | With a plan, show unconfirmed candidate slots for explicit selection. Without a plan, require the user to choose an upcoming meal. Confirmed `unspecified` logs remain visible as facts without assigning a slot. |
| More than one confirmed log for a type | Count and display the logs distinctly. Lock the meal type once. A confirmed snack does not advance the ordering of main meals. |
| Partial or zero nutrition coverage | Explain the data gap; offer a practical meal based on stated requirements. Do not optimize against calculated remaining calories or macros. |
| All main meals recorded or user says no meals remain | Show a finished state and skip generation. Snack is an explicit option only if the user identifies an upcoming snack and no snack has been confirmed. Never propose skipping a meal or compensating for earlier intake. |
| Invalid, historical, or out-of-date context | V1 replans today only. Keep historical records read-only. If the local day changes during the flow, discard the proposal for application and refresh. |
| Typed logs conflict with the user's selection | A confirmed slot cannot be replaced. An earlier unrecorded slot remains unknown; V1 does not backfill it after a later main meal is confirmed. |

Use the same `YYYY-MM-DD` and recorded-offset semantics as Log and Today. The browser obtains its current local date and time zone; the server can validate the selected today date against the supplied IANA time zone using `zoneinfo`. Existing records remain assigned to the local date already captured in their offsets, including after travel. The default main-meal ordering is breakfast → lunch → dinner. V1 does not infer whether an unrecorded meal was eaten from fixed clock cutoffs.

## State, persistence, and freshness

Step 7.2A uses a shared IndexedDB repository for Plan and future Replan. The browser database is `mealmind-meal-plans`, with a `plans` object store keyed by the selected local calendar date (`YYYY-MM-DD`). The picker defaults to the browser's local today. It can retrieve another date's plan and changing the selection discards the unsaved suggestion on screen. Store date keys as strings. The save timestamp is an independent UTC instant.

Each record holds a stable `planId`, `schemaVersion`, its active `revision`, and an ordered list of accepted snapshots. Revision 1 is the original. The last snapshot is active. Each snapshot retains its acceptance ID, save time, language, planning source, structured scope and constraints, and the accepted plan. Slots are keyed semantically by the backend's unique meal types, including snack when present. The scope records the request setting, and the accepted meal slots represent the actual generated scope. Natural-language input is not persisted. Review and re-enter any free-text requirements, including dietary restrictions, before later replanning. The store contains no raw model response, provider credentials, food logs, or images.

New suggestions are temporary. An explicit **Save plan on this device** or **Save as the active plan** action appends a snapshot. An IndexedDB transaction checks the previous ID/revision and whether the acceptance ID already exists. A duplicate acceptance is a no-op. A conflicting write reloads the current plan for user review before another explicit attempt. Invalid records are left untouched, and storage errors leave the temporary suggestion available. No SQLite table or food-log operation is involved.

Plans are specific to this browser profile, device, and origin. Clearing site data, private browsing behavior, blocked storage, and quota limits may remove or prevent persistence. The store does not sync with accounts or devices. For Replan previews, keep backend processing stateless and reuse this repository to apply the future accepted revision.

- Revisions apply to saved plans. A new proposal carries the date, target meal, request identifier, original plan ID/revision (or explicit absence), and confirmed-log context version. Cancel or navigation clears the unapplied proposal. Use request identity or cancellation to ignore late responses after a selection change.
- The context version is a deterministic digest of the date and ordered confirmed log IDs/revisions. Do not include raw user text in a digest response. Before application, refetch context; if a log or date changed, display a stale preview and require a new deliberate request. Recheck the target and expected plan revision inside the browser write transaction. An already applied proposal is a no-op. A newly saved plan also invalidates an older no-plan preview.
- Log writes and browser plan writes do not share a transaction. A confirmed log may arrive after the final check. When displaying the plan, confirmed history still takes priority and locks that slot; the stored suggestion remains a plan entry and never changes what was eaten. An atomic guarantee across plan and log writes would require a shared owner-scoped store, which is deferred.

## API and planner reuse

All new endpoints are development-only, using the same client/listener loopback, Host, and Origin checks as Food Logging. Use `Cache-Control: no-store`. Neither endpoint writes logs or plans. The frontend owns plan selection, preview display and explicitly accepted browser writes.

| Endpoint | Request and response |
| --- | --- |
| `GET /api/v1/replan/context?date=YYYY-MM-DD` | Validate the recorded ISO calendar date. Read confirmed logs using the existing query. Historical contexts can be read; preview is restricted to today in the supplied IANA time zone. Return date, context version, confirmed log counts by meal type and the locked types, plus an incomplete-history indicator. Do not return private descriptions. Use this endpoint for initial context and freshness checks without generation. |
| `POST /api/v1/replan/preview` | Body includes `date`, `timezone`, `expected_context_fingerprint`, `target_meal_type`, optional `current_plan` (plan ID, revision, date, source, and bounded meal plan), optional `planning_mode`, `constraints`, and optional `instructions`. The validated snapshot is supplied by the browser and is never assumed to reflect current storage. Reuse planning request constraint fields for language, ingredients, ingredient mode and time limit. Respond with the targeted meal using `MealPlanResponse`, a proposal ID, input plan/context identifiers, and structured notes that distinguish confirmed facts from assumptions. Return only the current target meal and the proposed replacement, plus untouched meal type identifiers. The response does not accept or persist either plan. |

Use `constraints.restriction_status` to explicitly report `none_declared`, `unreviewed`, or `present`. Unreviewed status requests clarification; declared critical restrictions currently block preview because there is no verified profile context. Unrecognized instruction clauses request clarification, and prompt-only requires inventory restrictions to be supplied as structured fields.

The preview route recomputes eligibility before generating and validates the result targets exactly one eligible type. Before returning, it rechecks whether the confirmed context or local day changed during generation. A stale context returns 409; an unavailable target or no remaining meal yields a structured no-generation outcome. Invalid or unsupported constraints use the existing validation/error patterns. Provider failure, timeout and unavailability remain distinct. No automatic retries. No log or plan is mutated on any error.

Reuse the current single-meal planning services. Avoid full-day generation followed by dropping completed slots: both current planners expect a full day to contain breakfast, lunch and dinner. Reuse catalog constraints, role coverage, diversity and effort ranking where supported. Catalog draft use keeps the existing opt-in, local access and review gates. Use deterministic catalog selection with personalization disabled by default. In prompt-only mode, at most one Gemini generation call per deliberate preview. Preserve the chosen mode and do not fall back between modes. Existing prompt-only checks cover result shape, meal type, time and strict ingredient lists, but do not independently verify arbitrary dietary or allergy restrictions. When a critical restriction cannot be validated with the selected path, stop for clarification or report unsupported. Do not silently strip it or relax constraints. Reconfirm scope-dependent free text when adapting a full-day request to one meal, and keep explicit compatible ingredient/time constraints.

Replanning adapts to the confirmed day by excluding eaten slots and letting the user review preferences for the next meal. To encourage variety, compare earlier explicitly typed confirmed item names against exact catalog labels. Catalog mode uses matched recipe families as a diversity signal. Prompt mode receives only up to 12 matching catalog labels as soft hints. Unknown and unspecified history provide no variety hints. The API does not send raw confirmed descriptions, photos, portion amounts, or actual intake estimates to Gemini. The preview can display availability of nutrition coverage from the existing read-only analysis when already loaded. It never feeds a calorie or macro gap into the planner, even if every recorded item was calculated. Favor practical one-person meal templates and existing complete-meal quality rules without expanding the recipe catalog.

## Step 7.3 acceptance and slot merge

Today compares the current IndexedDB plan ID and revision with the preview's base, and fetch a fresh context fingerprint for the same date before applying. If either changed or the target is no longer eligible, leave the active plan alone. Reject applying after a local date change. Use the IndexedDB write transaction's revision check for the final commit.

Planning and Replan use the same repository. Within the write transaction, a single-meal acceptance replaces or adds only its own meal type. The current plan ID and all prior snapshots are preserved. Untouched slots keep their planning settings; older snapshots without explicit per-slot settings use their existing snapshot settings. A new full-day plan can still create a complete active revision through Planning. Replan uses the proposal ID as the acceptance ID and accepts only after checking both the latest confirmed-log fingerprint and current plan version. A failed write leaves the preview unapplied and visible for a possible manual retry.

The context read and IndexedDB write do not share a transaction. A log can change after the final read but before the browser writes. The next context read will reflect the confirmed log and lock its slot. Application of a preview never changes actual consumption records.

## Implementation and verification

1. Step 7.2B adds a slot/context service and tests for confirmed filtering, typed/unspecified logs, duplicate types, snacks, all meals complete, same-day records with mixed offsets, and midnight rollover. Factor existing development access guards into the preview route as needed. Verify reading adds no SQLite writes.
2. Step 7.2B adds the typed context and preview contracts. Use mock providers to test selected-target enforcement, previous requirements, hard constraints and uncertainty, no-call outcomes, a maximum of one model call, partial/empty nutrition independence, no fallback, stale context during generation, and redacted errors. Confirm existing planning routes behave as before.
3. Step 7.3 reuses the shared browser store and meal cards for the explicit Today flow. Test preservation of original plan and other slots, no-plan acceptance, cancel, refresh, duplicate apply, two-tab revision conflicts, unavailable storage, date rollover, late responses and records changing between preview and acceptance. Verify both languages and mobile layouts, and test that a production build cannot request private endpoints.

Deferred: multi-meal atomic replans, restaurant-mode UX, automatic reminders or regeneration, personalized nutrient targeting, inference of unlogged meals, pantry deductions, public guest/owner persistence, multi-device sync, assistant routing, and richer revision history. Review the browser persistence boundary, one-meal limit, and supported privacy and dietary behavior before implementation.
